# PARIS source repair

PARIS exposes admissions, instruction, operations, engineering, quality and supervision through one identity and the existing governed tools. ELLIE/LIZZY/ZORA are compatibility capability IDs; Store licensing remains separate.

The previous engineering endpoint committed edits to main before tests. It now stages a bounded patch and queues a durable `paris_code_repairs` record. The authenticated endpoint retains its existing administrator boundary. A service-only owner policy enables automatic diagnosis of recurring unresolved quality/unknown events and terminal Course Builder quality failures. The latest job must still be the failed job; an active or recovered build is never treated as that historical failure.

The trusted `PARIS verified code repair` workflow runs every ten minutes to dispatch work, with one active repair globally and a maximum of three repair incidents per day, each with at most two attempts. Dispatch is not execution evidence. A separate workflow stages the patch using the shared configured AI gateway and its existing spending authorization (owned inference remains available only through a configured Google endpoint), requires a new regression test, runs that test and shared regression suites, records an immutable candidate receipt, and type-checks Admin/LMS/Marketing. Candidate code receives no production secrets or write token. Existing tests, auth, credentials, payment code, quality gates, release controls, and the repair control plane cannot be autonomously changed.

Publication independently reads the workflow validation job and confirms the exact candidate branch SHA. A non-force fast-forward requires main to remain at the recorded base. Conflicts preserve task-branch work and require reconciliation. The existing Google deployment workflows receive explicit dispatches. `verified` requires successful deployment workflows and the exact immutable SHA served by all three apps; it does not mean a course video passed QA. A failed course can be requeued through the canonical job queue after verified code delivery, preserving the original failed job and checkpoints. Existing owner pauses remain authoritative.

Durable phases: queued, dispatched, patching, validating, deploying, verifying, verified, blocked. A failed or lost workflow is visible as blocked. Admin supervision shows execution links and error codes. Missing evidence, credentials, billing, protected changes and failed tests do not become synthetic success or unchecked retries.

Validation: policy regressions, mocked publication and authority checks, existing unified engineering/identity/preview regressions, lint, application type checks, and production build/deployment checks. Live completion requires a real recorded repair, not this document or a scheduled workflow alone.
