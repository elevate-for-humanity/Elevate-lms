     - supabase.auth.getUser() → user.id
     - supabase.from('profiles').select('role').eq('id', user.id).single()

SECTION 5: ROLE ARCHITECTURE
==============================

TWO ROLE SYSTEMS EXIST (one active, one dormant):

System 1: profiles.role (ACTIVE)
  - Global flat role field on profiles table
  - Default: 'student'
  - Values used in code: student, admin, super_admin, instructor, staff,
    board, program_holder, delegate
  - Enforced in 296 API route handlers via:
      profiles.select('role').eq('id', user.id).single()
      if (!profile || !['admin'].includes(profile.role)) return 403
  - NOT tenant-scoped (a user has ONE global role)

System 2: user_roles table (DORMANT)
  - 0 rows
  - Has tenant_id column (tenant-scoped by design)
  - Referenced by lib/requireRole.ts (4 queries)
  - Supports: sponsor, employer, workone, admin
  - Has permission mapping via getRolePermissions()
  - NOT used by any API route currently

System 3: withAuth wrapper (ACTIVE, partial adoption)
  - lib/with-auth.ts: wraps API handlers, injects user + role
  - Reads role from profiles.role (System 1)
  - Used by ~30 admin API routes
  - Does NOT check tenant_id

System 4: authGuard (ACTIVE, partial adoption)
  - lib/authGuards.ts: server component auth guard
  - Reads role from profiles.role (System 1)
  - Supports allowedRoles array
  - Does NOT check tenant_id

VERDICT: Roles are enforced in API routes (not just UI), but enforcement
is GLOBAL (profiles.role), not tenant-scoped (user_roles). A user who is
'admin' is admin across ALL tenants.

RECOMMENDATION: Migrate the 8 code queries from 'users' to 'profiles'.
Reconcile the 155 orphaned users rows. The 'users' table should become
a view or be deprecated.
